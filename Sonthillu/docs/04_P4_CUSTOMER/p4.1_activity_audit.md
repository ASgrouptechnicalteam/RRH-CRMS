# Phase P4.1 (Customer Activity Synchronization) Audit

## Current Architecture

- **CustomerActivityProvider:** Hardcoded to 'guest' mode. Reads/writes exclusively to `localStorage`. Does not synchronize with the authenticated Web DB.
- **Guest-to-Account Migration:** Does not exist. Guest activity is discarded or ignored upon login.
- **ActivityEvent Tracking:** Client-side event dispatcher (`trackCustomerActivityEvent`) is set up, but no listener forwards these events to the server action (`trackActivityEventAction`).
- **Server Identity:** `auth.ts` securely issues sessions and `session.ts` correctly extracts customer identity, but the activity endpoints do not enforce strict schema validation or batch limits on client payloads.

## Security & V1 Blueprint Violations in Current Code

- **No Client Payload Validation:** Existing actions (`addToShortlistAction`, etc.) lack strict size limit checks and array validation.
- **Missing Migration:** Guest state is lost because there is no robust mechanism to upload local storage arrays to the server after authentication.
- **Root Layout Rendering:** Relying on Server Components to inject the authenticated state in `layout.tsx` would ruin static site generation for public pages. The V1 Blueprint demands performance preservation.

## P4.1 Requirements

- **Server-Authoritative Identity:** Use `getCurrentCustomer()` strictly. Ignore client-provided customer IDs.
- **Idempotent Migration:** Guest states must be merged securely, limiting payloads to reasonable bounds (e.g., 50 properties max), with set-union deduplication.
- **Failure Resilience:** `localStorage` must only be cleared _after_ the server confirms a successful DB transaction for the migration.
- **Activity Tracking Privacy:** Event tracking must strip PII, relying exclusively on server-derived identity.
