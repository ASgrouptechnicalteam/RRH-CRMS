# Phase P4.1 (Customer Activity Synchronization) Implementation Plan

## Goal Description

Execute the **Guest → Account Migration & Customer Isolation** phase (P4.1). This plan safely connects the client-side `CustomerActivityProvider` to the Sonthillu Web DB using strictly authenticated Server Actions. It guarantees customer isolation, ensures non-destructive and idempotent guest activity migrations, and persists `ActivityEvent` payloads without jeopardizing the statically generated nature of public pages.

## Proposed Architecture

### 1. Initial State Fetching via Server Action

- Create `getCustomerActivityStateAction()` in `src/app/actions/customer.ts`.
- This action will call `getCurrentCustomer()`. If the user is authenticated, it fetches their Shortlist and Compare arrays directly from the Web DB.
- Returns `{ mode: 'customer', shortlist, compare }` or `{ mode: 'guest' }`.
- **Why?** This prevents the root layout from becoming a Dynamic Server Component and preserves SSG performance.

### 2. Client Provider Refactoring (`CustomerActivityProvider.tsx`)

- Implement a `useEffect` hook that mounts and calls `getCustomerActivityStateAction()`.
- If the server responds with `mode: 'customer'`, the provider updates its internal state to reflect the authenticated data.
- **Migration Trigger:** If `mode: 'customer'` AND the browser's `localStorage` contains guest Shortlist or Compare items, the provider will automatically invoke the `mergeGuestActivityAction()`.
- **Safe Cleanup:** Guest `localStorage` will **only** be cleared if the merge action explicitly returns success. If it fails, the guest state remains untouched and a safe retry mechanism can be implemented.

### 3. Server-Authoritative Merge Action

- Refactor `mergeGuestActivityAction(guestShortlist, guestCompare)` in `src/app/actions/customer.ts`.
- **Validation:**
  - Ensure inputs are valid arrays of numbers.
  - Reject arrays exceeding reasonable batch limits (e.g., maximum 50 properties).
- **Identity Enforcement:** Rely purely on `getCurrentCustomer()` for the target account. Ignore any client-provided user IDs.
- **Idempotency:** Utilize the set-union behavior. Valid IDs will be appended to the authenticated user's Shortlist and Compare items via the existing `service.ts` logic, respecting the `COMPARE_LIMIT`.

### 4. Activity Event Persistence

- Wire up a `window.addEventListener(CUSTOMER_ACTIVITY_EVENT_NAME)` inside `CustomerActivityProvider.tsx`.
- The listener intercepts dispatched events and forwards them to `trackActivityEventAction()` (`src/app/actions/analytics.ts`).
- Inside the server action, derive `customerId` securely from `getCurrentCustomer()`. Strip any untrusted user ID metadata provided by the client, maintaining absolute isolation and privacy.

## Verification Plan

### Automated Tests

- Validate TypeScript adherence via `npm run typecheck`.
- Validate static building boundaries via `npm run build` (Ensuring `/about`, `/contact`, and `/` remain efficiently static `○`).

### Manual QA Matrix

1. **Guest Migration:** Browse as guest. Add Property A to Shortlist. Log in. Confirm Property A ports successfully to the account, and `localStorage` is completely wiped.
2. **Duplicate Merge:** Add Property B as a guest. Log in to an account that _already_ has Property B in its shortlist. Confirm no DB duplicates occur.
3. **Customer Isolation:** Log into Customer A. Add Property C. Log out. Log into Customer B. Confirm Property C is invisible to Customer B.
4. **Activity Persistence:** Click "Shortlist" and observe the network request forwarding the payload to the server action. Verify the row appears in the local XAMPP MySQL `activity_events` table.
5. **Forged Payloads:** Attempt to execute `mergeGuestActivityAction` with oversized arrays (100+ IDs) or invalid string IDs. Ensure the server gracefully rejects them without crashing.
