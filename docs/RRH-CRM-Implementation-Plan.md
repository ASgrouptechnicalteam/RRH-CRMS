## How to use this document while implementing

Read this section before starting any task below.

1. **Work one task at a time, in order within a phase.** Phases are ordered by risk and dependency — later phases assume earlier ones are done (e.g., don't build the Project workflow engine in Phase 2 on top of data-isolation bugs that Phase 1 was supposed to fix first). Within a phase, tasks can usually be done in any order unless a task says otherwise.

2. **Before touching code for a task, re-read the exact file(s) and line references cited.** The audits were read on specific dates against a specific state of the code; if the file has changed since, re-verify the finding still applies before "fixing" something that may have already moved.

3. **Never fix a finding by deleting the feature unless the task explicitly says to.** E.g., the CALL_LOGGED guard gap should be fixed by adding the guard, not by deleting the comment that mentions it. The Customer Portal stub should be either finished or clearly marked "coming soon" in the UI — not silently removed.

4. **Every workflow/authorization change needs a test before it's considered done.** For the workflow-engine tasks in Phase 2 especially: write (or extend) a Jest test that exercises the exact bypass or gap described, confirm it fails against the old code, then confirm it passes against the fix. This is the only way to know a "fixed" workflow bug doesn't quietly regress later.

5. **Do the fix, run the app locally, manually exercise the affected flow end-to-end (not just the unit test) before checking the box.** For anything touching Lead/Property/Project status, that means: log in as the relevant role, perform the action in the actual UI, and confirm the database state and the UI both reflect what's expected.

6. **Commit per task, not per phase.** Small, reviewable commits. Reference the task number in the commit message (e.g., `fix(P2-3): remove double-mount of apiRateLimiter`). This makes it possible to bisect if something breaks later.

7. **Do not run destructive database operations** (`prisma migrate reset`, dropping tables, force-pushing schema changes to the production/Hostinger database) without an explicit, separate confirmation from Sandeep at that moment — audits and plans are not blanket permission for destructive steps.

7a. **Production database changes are deliberately deferred (decided 2026-09-06).** Every fix in this plan is implemented and verified against the local `test_db` (XAMPP, `127.0.0.1:3306`) only. Any change that would eventually need to touch the production database (schema migrations, data seeds/backfills) gets implemented and tested against `test_db`, then logged in `docs/PENDING-PRODUCTION-CHANGES.md` instead of being applied — production stays untouched until the entire plan is complete and verified end-to-end (frontend and backend), at which point that file is worked through deliberately in one pass. Do not apply anything to production early, even something that looks small and safe.

8. **When a task is marked "needs a product decision,"** stop and ask before implementing — these are places where the fix depends on how the business actually wants the feature to behave (e.g., "should a rejected property notify the PM and go back to PENDING_VERIFICATION, or does MD rejection need a different path than PM rejection?"). Guessing here produces a plausible-but-wrong feature.

9. **Update the summary tracker in §8 as phases complete**, so it's possible to see overall progress at a glance without reading the whole document.

10. **Before running ANY script or test command that touches the database, confirm it's actually connected to the test/staging database, not production** — don't trust an env-var name alone. Phase 0.3 found a real bug where a test-setup file's own "safety guard" printed a reassuring message while a shared database client had already silently connected to production, because of import-ordering, not a wrong env-var value. The pattern to watch for: any file that constructs a `PrismaClient` (or any DB client) needs its connection string finalized _before_ that construction happens — not "eventually," not "by the time the tests run" — because clients lock in their connection at construction time. When adding new scripts that touch the database, copy the guard pattern now in `tests/api/setup.ts` and `scripts/wipe-sample-data.ts` (verify env value → set `process.env.DATABASE_URL` → _then_ construct/require the client → then re-verify with a live `SELECT DATABASE()` query before any write).

- [x] **0.3 Fix the test-database isolation bug BEFORE running any tests.** _(2026-09-06 — done)_ Found and fixed a real bug that matches exactly the concern raised about this phase: running the test suite could have altered production data.
  - **Root cause:** `apps/api/src/lib/prisma.ts` runs `export const prisma = new PrismaClient()` at module-load time. A `PrismaClient` locks in its connection string from `process.env.DATABASE_URL` **at the moment it's constructed** — reassigning that env var afterwards has no effect on an already-built client. `tests/api/setup.ts` had `import { prisma } from '.../lib/prisma'` as its very first line, which — because `import` statements execute before the rest of the file's code — constructed the shared Prisma client **before** `.env.test` was loaded and before the file's own "Phase 0 test database safety guard" checks ran. Depending on whatever `DATABASE_URL` happened to already be present in the environment at that instant, the entire test suite's shared database client could have been pointed at production while the console output claimed the safety guard had passed.
  - **Fix applied:** reordered `tests/api/setup.ts` so `.env.test` is loaded, every guard runs, and `process.env.DATABASE_URL` is set to the verified test URL **first** — the shared `prisma` client is now `require()`'d only after all of that succeeds (a deliberate `require()`, not a top-level `import`, so it can't be hoisted ahead of the guard again by a future edit). Added a further runtime check in `beforeAll` that queries `SELECT DATABASE()` and aborts the whole run if the _actual_ connected database isn't `test_db` or `u988844918_test` — this protects against the same class of bug even if the import-order fix is ever undone by accident.

It now refuses to run unless `.env.test`'s `DATABASE_URL_TEST` resolves to a recognized test database name AND an explicit `CONFIRM_WIPE_TEST_DB=yes-wipe-the-test-database` environment variable is set, with the same live `SELECT DATABASE()` check before any delete runs.
